# 三、实现方式与我建议的三处分歧（需要你知道）

**1. 恢复用的是「逐包重放」不是「合并增量」**

我建议把 gap 期间的变更合并成一个 delta 包；仓库选择了保留每一代的原始包逐个重发：

```2:2:src/packet-history.js
// Bounded, shared per-room history. Every entry is one original generation.
```

README 也明确写着「不合并多代」。这是**更保守也更正确**的选择（每代顺序独立可验证），代价是重放 N 代就是 N 倍流量。文档自己承认了这一点：

> 历史重放对短时背压减少全量快照，但不会创造网络容量：默认 v1 的上述极端负载仍需约 40MB/s 单客户端。超过历史窗口或长期传输不足仍会快照恢复。

也就是说：**短时抖动解决了，长期带宽不足没解决**。

**2. 小地图是「单方面替换」而不是「双模式」**

我建议保留精确模式给测试、性能模式给生产；他们直接把精确模式删了，README 第 315 行：「像素级小地图像素等价要求不再适用于本轮」「单个微小结构不保证旧版像素覆盖」。方向和我一致（接受近似换性能），但**回归网变弱了**——原来 212 项小地图像素对照不再适用，需确认 `test:browser:equivalence` 现在还剩多少有效覆盖。

**3. GPU 与 v2 被设为默认，但默认组合不是最优组合**

`src/runtime-defaults.js` 让 `npm start` 默认 `LIFEWAR_EVOLUTION=gpu` + `LIFEWAR_BOARD_PROTOCOL=2`。而上表显示 **GPU+v2（18.04）比 GPU+v1（19.88）慢**。也就是说默认启用的是"带宽更省但更慢"的那一档，而不是最快的那一档。密集场景下带宽不是瓶颈（瓶颈是 tick CPU），这个默认值有讨论空间。

# 四、新引入的风险与技术债

1. **实验后端被设为默认**：GPU 标注为"实验后端"，回退路径有 5 条（无设备 / 无 `webgpu` 依赖 / 初始化失败 / 单代等待 >100ms / 局部法则生效期间），且"小负载不保证更快"。同时 `webgpu` 是原生可选依赖，装上就多一层安装失败面。
2. **直接 terminate 原生 Dawn worker 会导致进程无日志退出**——文档记录了这个坑并改为等待在途作业，但"失去响应的设备会被弃用并解除 worker 引用，可能保留资源到服务器退出"意味着潜在的 GPU 资源泄漏。
3. **死代码残留**：`renderer.js:334-337` 仍在传 `paintCell` 回调，但新的 `MinimapCache.draw(field, paintBackground, paintBases)` 只收 3 个参数；`renderer.js:84/91` 仍在调 `beginPacket()` / `change()` 这两个空实现。
4. **文档自相矛盾**：README 274 行（T13 历史段）仍写"默认仍为 v1"、278 行写"默认保留 v1"，靠 256 行一句"当前运行脚本已改为 GPU＋v2"兜底。历史段不改写会让后续阅读者误判。
5. **v2 的额外成本**：每房间 +1MB 基准棋盘，空包 8B→32B。

# 五、剩余优先级建议

| 优先级 | 动作 | 理由 |
|---|---|---|
| **P0** | 把默认组合改成 **GPU+v1**（或让 v2 只在 `PUBLIC_URL` 公网模式默认） | 实测快 1.8 代/秒；密集场景瓶颈是 tick 不是带宽 |
| **P0** | 补 `test:browser:equivalence` 的有效覆盖说明 | 像素等价被放弃后，需明确剩余回归边界，否则是静默风险 |
| **P1** | `next.fill(0)` 改候选位清零；休眠快照改按需拷贝 | 稳态省 40MB/s，与细胞数无关的固定税，低风险 |
| **P1** | `placement()` 去掉每帧 `JSON.stringify` | 改标量指纹即可，纯收益 |
| **P1** | 清掉 `MinimapCache` 的空实现调用与 `paintCell` 死参 | 避免后人误以为小地图还在逐格绘制 |
| **P1** | `npm run benchmark` 增加 50 万细胞档 | 让 `benchmark` 与实际失败区间对齐 |
| **P2** | 房间移入 worker_threads | 文档已自认这是下一步（多房间 + 百万细胞） |
| **P2** | 长期不足时的**合并增量**作为逐代重放之外的第二档 | 补上"超过 32 代窗口"的降级路径 |
| **P2** | `/api/patterns` 鉴权 + 原子写 + 条数上限 | 公网部署的实际安全问题 |

**一句话**：上一轮我判断的三个架构锁（小地图像素等价、丢代即全量快照、单线程无容错）**已经解开两个半**——小地图从 269ms 降到 1ms、恢复从 3.2MB 降到逐代重放、房间异常不再拖垮全局，50 万细胞场景首次做到零漏收零恢复。剩下 worker_threads 隔离和"长期带宽不足"这两条仍是硬骨头，而 GPU 只拿到 15%–21% 的单代收益、且尚未认证百万细胞与多房间。
