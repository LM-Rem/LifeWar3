### T07：规则与几何

- 全局 B/S 每代从原 Set 编译为 9 位掩码；不缓存 Set 的对象身份，原地修改规则也不会失效遗漏。
- 局部规则按 32 格瓦片建立候选列表，仍使用精确圆域判定、最后规则优先。签名包含位置、半径及 B/S 掩码；到期由原 expireCardEffects 删除后触发重建。0 条局部规则不走索引查询。
- nearby 的整数圆域按原 yy/xx 顺序缓存 Uint32 key 列表，实际读取 board 和回调仍逐代执行。几何变化使用新缓存键；最多 128 个圆域。非整数参数保留原循环行为。
- 领地的整数格索引在同一几何累计 512 次查询后建立，避免为少量操作支付全图初始化。1000×1000 使用 2,000,000 字节 Int16；分界平票仍属于原列表较早站点，节点易主/基地淘汰只影响实时 owner，不重建几何。重新生成领地得到新缓存；直接修改站点几何须调用 `invalidateTerritoryIndex()`。分数和非法坐标继续使用原逻辑。
- 旋转/翻转/选择产生的新图案数组拥有独立包围盒缓存。预览依赖棋盘修订、状态、能量/容量/淘汰、节点归属、相机投影后的格坐标、阵营、图案和道具目标；命中时复用验证结果，画面仍逐帧绘制。缓存图案数组视为只读，编辑后使用新数组。
- AI 继续使用原调用顺序，通过共享领地查询间接受益，没有改动其决策或 RNG。

### T08：两个后端与严格顺序

sparse 保留从 alive 出发的候选拓展；dense 逐行读取旧棋盘八邻居并计算计数与阵营票，再按原 alive/self/dy/dx 顺序恢复候选。两者共用规则应用、同化、nextAlive 和变化发布逻辑。

内部格子的八邻域展开为固定顺序，边界继续走原有裁剪循环。不改变 self、左上/上/右上/左/右/左下/下/右下的访问顺序。也不将 B0 扩展到原引擎未覆盖的远处空格；既有候选语义保持一致。

dense 的计时包含完整顺序恢复。测量没有找到足以晋级 auto 的稳定优势，因此 **不引入未经验证的交叉阈值、滞回或最短驻留策略**；auto 固定使用当前可用最佳 sparse。此项按方案的收益门槛收敛，不能表述为“密集自动切换优化已通过”。

`LIFEWAR_EVOLUTION=sparse|dense|auto` 可在新游戏选择；默认 auto。测试可在 step 之前改变 selector.mode，切换只在代边界读取，复用棋盘和顺序缓冲，不重置年龄、规则、RNG 或历史。强制逐代切换测试保留每个切换代的耗时。

### T12：接收与绘制分离

生产 WebSocket 回调使用 receivePacket/receiveState，低层 updatePacket 仅在 RAF 内被队列调用；同一主画面绘制前最多应用一个包，无新包仍绘制相机和动效。没有固定播放缓冲，空增量也独立提交。generation HUD 跟随显示代，约 5Hz 状态、休眠、卡牌和胜负只在不晚于显示代时应用。

v1 存在“同代最终修订”：例如断线淘汰在没有新演化的情况下改变棋盘。队列允许不同内容的同代包各自绘制，丢弃字节相同的重复包；同代还有待绘制包时延后应用该代的最终状态，防止先显示结局。v1 没有 wire epoch/revision 字段，旧连接通过 socket 身份拦截，新 started/reset 建立本地 epoch；不能把这一机制描述为已经实现 T13 的协议 epoch。

默认限制：32 包、64 MiB 待用包、最老待用包 500ms；状态队列最多 64 个不同代。超限、缺代或格式错误记录 failure，清空待用区并请求 resync；隐藏标签关闭连续区间，恢复可见后请求快照。恢复明确记为新区间，不伪造中间代已经绘制。重置丢弃尚未显示的旧 epoch 包会记录 cancelled。failure 计数、最后失败原因和最大深度即使 trace 关闭也保留在队列对象中。

服务器新增当前会话的 resync 请求：返回独立棋盘快照和该玩家可见状态，不重开对局；限制请求频率，发送缓冲高于原阈值时等待恢复，避免无限追加快照。客户端等待恢复时最多每秒重试，防止一次限频使其永久卡住。原有服务端背压快照同样记为恢复事件。

部署/施卡仍由权威服务器判定，预览使用已显示棋盘；trace 记录操作时的接收/显示代差和拒绝时的积压。没有为了追赶队列覆盖尚未展示的正常增量。

## 服务端性能

每场景 baseline/auto/dense 交错各 5 个独立进程，预热 30 代、测量 100 代。基线是本次开始时的 T06 引擎；冻结 20Hz 合成配置，固定时间、高 HP、高休眠阈值；计时仅包含 step+packet，不能代替完整服务端 tick、网络或多房间容量。

| 场景 | T06 平均 ms | auto 平均 ms | dense 平均 ms | auto p95 / p99 ms | 平均耗时下降 | auto 超 50ms /500 |
|---|---:|---:|---:|---:|---:|---:|
| P01 | 1.593 | 1.092 | 7.680 | 1.368 / 1.757 | 31.4% | 0 |
| P03 | 30.332 | 20.968 | 22.057 | 22.673 / 23.818 | 30.9% | 0 |
| P04 | 63.054 | 48.886 | 52.783 | 52.658 / 57.586 | 22.5% | 82 |

P01 为 24,000 静物；P03 测量期约 82–92 万细胞扩张；P04 约 50 万细胞且每代约 50 万变更。P04 基线 500/500 次超期，auto 仍有 82/500 次超期，最大 80.475ms，**没有通过零超期门槛**。这些也只是 step+packet，不以 P03 的 p95<25ms 冒充完整 tick 的认证。

交叉点探索中 dense/sparse 平均耗时比约 0.962–2.994。唯一小幅领先的 80 万初始细胞、1 条局部规则组合约快 3.8%，不足以作为稳定晋级依据；保留 sparse 的相对损失仍低于 10%。强制每代切换的 P04 单轮平均约 49.790ms、p95 53.098ms、46/100 次超期，没有剔除切换代。

完整 p50/p95/p99/max、超期数、逐轮均值、L/C/D、内存及源码/环境信息见 [机器可读汇总](t07-t12-summary.json)。另测初始 10/30/50/80 万细胞、0/1/8 条局部规则的交叉点；这是每组合单轮探索，不能把小幅差异当稳定优势。原始数据保存在 artifacts/performance/t08-crossover。

## 客户端与实时范围

真实联机短测在包含启动与人为消息停顿的区间内，收到的前 118 代均已独立提交绘制（末尾两代作为在途尾部单独排除），没有正常区间内的缺代恢复，状态 generation 均不大于显示代。配置 20Hz，实测接收约 16.54 代/秒；headless RAF 间隔 p50 4.2ms，本机并非固定 60Hz，因此标准 20Hz/60Hz 关系另由确定性单元模拟验证。

接收后排队 p50 2.8ms、p95 10.5ms、p99 188.0ms、max 199.3ms；最大待绘制深度 4，超过方案正常 ≤2 代目标，峰值发生在启动初期。该数值仅为本机接收到应用前的排队，不能当作权威提交到物理显示的时延。**队列功能验证通过，但包含启动的实时门槛未全部通过。**

受控预览测试中 4096 格验证连续 100 次，缓存约 0.2ms、原验证约 19.1ms；这是单次会话的 JS 验证耗时，非整帧时间，Canvas 仍需绘制原图案。

真实联机测试保留启动阶段和一次 200ms 消息延迟后的有序释放，不删掉慢样本。其输入配置为 20Hz，实际接收节奏和 RAF 间隔另行记录；**配置频率不等于实测频率**。本机接收间隔出现约 62ms，尚未定位为特定系统或调度原因，不据此承诺实际达到 20Hz。

功能范围内没有静默跳代；启动阶段积压与高负载恢复仍意味着实时能力不足。更低端设备、真实后台限频、LAN 输入到处理/呈现的时延、30 分钟/2 小时稳定性和密集客户端负载未完成认证。T12 功能阶段完成，整项目的“不跳帧实时运行”认证仍保留为 NOT RUN / 未全部达标。
