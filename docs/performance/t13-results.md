# T13 协议优化实施与验证

日期：2026-09-24。v2 功能实现完成，默认晋级门槛尚未通过，默认仍使用 v1。协议格式、会话边界与校验约束见 [协议文档](../board-protocol-v2.md)。本轮没有实施 T14–T17 或 CUDA。

## 交付

新增共享 `public/board-protocol.js`。v2 使用 32 字节明确包头，携带 version、roomEpoch、generation、baseGeneration、encoding、payloadLength、计数；不与 v1 的 0/1 标记混淆。

- ordered24：每个有序条目 3 字节，保留首次触及顺序和最终 owner。快照始终使用该编码。
- tiled：32×32 格瓦片内自动选择 sparse uint16 或 dense-byte；附加有序新生 key 表。比较包含全部元数据的完整大小，只有严格小于 ordered24 才选择。
- 服务器握手协商、混合版本广播、按版本复用包、独立 roomEpoch。快照后首个增量强制有序，避免广播基准与中途快照的存活状态不同。
- 客户端复用逐代呈现队列；完整包校验后入队，应用前验证新生与已呈现棋盘一致。队列内存包含解码数组，缺基准及超限明确恢复。小端主机上的 v1 解析复用原始包视图，不再为队列保留一份相同条目数组。

启用 v2 的服务器增加约 1MB/房间的广播基准棋盘；默认 v1 不分配。v2 每包仍代表单代，没有减少发送频率、合并世代或改变游戏规则。消息上界低于 4MiB，无需应用层分片。

## 正确性与兼容性

- `npm test`：130 项通过，0 失败。
- 1000 代随机写入与 v1 比较完整棋盘、Map 内容与插入顺序；包含生死反复、owner 0–4、快照、边界瓦片及编码切换。
- 阈值两侧、混合 sparse/dense、新生元数据抵消压缩收益、错误版本/长度/owner/坐标/计数、重复瓦片/格子、非法填充及新生表均有定向覆盖。
- 四个真实 WebSocket 客户端混用 v1/v2，比较每条消息相对该连接 v1 基线的棋盘与顺序。以确定性 bufferedAmount 注入触发背压，验证跳过后的显式快照、首代有序增量及恢复瓦片编码。另覆盖 v1-only 发布配置。
- 新浏览器客户端连接新、旧服务器均通过握手及刷新恢复会话测试；重连同一对局保持 epoch。
- 冻结原始渲染器对照：既有 212 项，加协议场景 64 项，共 **276 项主画面/小地图 PNG 比较**；另有 32 项浏览器有序 Map 哈希比较。覆盖 DPR 1/2、密集变色、删除、逆序新生、空代、同代修订和恢复。
- v2 的确定性 20Hz 输入/60Hz RAF 测试完整提交 201 个世代，无恢复。实际前台 WebSocket/RAF 回归亦通过，但其实际输入约 16.5Hz，不能用作物理 20Hz 认证。

真实前台回归使用普通练习负载，含 200ms 消息延迟后按序释放和模拟 visibility 事件。正常区间收到的世代截至第 117 代均有独立绘制提交，正常区间无恢复；队列峰值 4、最大等待约 197ms，启动与突发仍超普通队列深度≤2的目标。隐藏恢复是显式恢复区间，不算正常连续区间不丢代。未完成真实后台节流、低端设备或密集前台 20Hz 认证。

## 验证中发现并修复的小地图问题

新增“密集细胞集中在局部区域”的夹具发现原 T11 局部裁剪重绘与完整重绘存在 PNG 差异，v1/v2 均可复现，棋盘与顺序相同。原先全图分散夹具通常触发全量回退，因此没有暴露这一边界。

现在贡献者在原坐标下完整栅格化到复用的 scratch Canvas，再复制整数坐标的不透明瓦片；不再裁剪单个亚像素矩形。贡献者总工作量超过全体细胞时全量重绘。新增及原有像素检查均通过。180×180 小地图 scratch 像素存储约 126.6KiB，浏览器实际画布开销另计；本轮不重述上一阶段密集重绘性能数字为当前版本实测。

## 带宽与 CPU 测量

固定 1000×1000 棋盘，在一个 Node 进程中进行 5 轮交错版本测量，每轮预热 3 次、测量 10 次，每项共 50 个样本。每次从独立相同基准开始，包外准备和 Map 复制不计时。CPU 合计为编码、校验解码/顺序恢复及 board/Map 应用，不包含演化、Canvas、网络延迟和 room 基准维护；不是服务端 tick 或真实端到端延迟。

v1 CPU 路径采用本轮共享解码器，不是旧版浏览器的历史完整耗时。所有负载为合成协议负载，不把几十万细胞容量当作合法长期对局。完整环境、参数、P95/max、源文件 SHA256 在 [机器可读汇总](t13-summary.json)。

| 场景 | v1 → v2 完整包字节 | 包体总量下降 | 编码+解码+应用均值 ms：v1 → v2 |
|---|---:|---:|---:|
| 空代 | 8 → 32 | 增加 24 字节 | <0.1 → <0.1 |
| 分散 1000 条更新 | 4008 → 3032 | 24.4% | 0.083 → 0.137 |
| 80 万既有细胞变色 | 3,200,008 → 1,013,702 | 68.3% | 35.65 → 77.62 |
| 50 万条更新，半数新生 | 2,000,008 → 1,500,032 | 25.0% | 27.80 → 36.59 |
| 50 万条全新生 | 2,000,008 → 1,500,032 | 25.0% | 30.32 → 39.28 |
| 50 万细胞快照 | 2,000,008 → 1,500,032 | 25.0% | 35.52 → 39.39 |

80 万变色情景中，v2 编码均值约 16.15ms，校验解码/顺序处理均值约 18.08ms、P95 约 28.50ms。它显著节省网络字节，但 CPU 成本明显增加，不能宣布“压缩即加速”。半数及全部新生场景均自动回退 ordered24；表中已经包含顺序数据成本，不使用理论 3bit 棋盘大小冒充实际包大小。

按四客户端、棋盘 20Hz、私有状态 JSON 5Hz，并加入未掩码 WebSocket 帧头投影：80 万变色情景从约 **256.04MB/s 降至 81.14MB/s**；50 万高新生场景从约 **160.04MB/s 降至 120.05MB/s**。这些为十进制 MB 的需求投影，包含真实序列化的私有状态大小，但不包含 TCP/TLS，也不是已达到的网络吞吐能力。快照不按 20Hz 投影。

四客户端 loopback 测试另记录实际发送的二进制、JSON 与 WebSocket 帧头字节，并为每个 v2 连接生成同一发送序列的 v1 等价流量，避免将慢连接少收到包误当作压缩收益；记录见汇总的 network 部分。

## 发布决定、复现与后续

**v2 功能验证通过；高密度端到端实时门槛未全部达标，因此默认保留 v1。** 编码器内部按完整包字节数选择模式；五轮 CPU 结果用于阻止未经验证的默认晋级，而不是宣称当前模式选择已经达到全局最优。3bit-packed/RLE 尚未加入，继续提高压缩率应先降低现有的编码扫描、顺序验证及 Map 应用成本。

显式试用 v2：

```powershell
$env:LIFEWAR_BOARD_PROTOCOL='2'
npm start
```

回退时设置为 `'1'` 或移除该环境变量，并重启服务；现有游戏不会热切换协议。两种模式都保留本轮小地图正确性修复。没有自动提交、部署或更改平衡参数。

验证命令：

```powershell
npm test
npm run benchmark:protocol
npm run test:browser:protocol -- --playwright <Playwright目录> --executable <Chrome路径>
npm run test:browser:equivalence -- --playwright <Playwright目录> --executable <Chrome路径> --output artifacts/performance/t13/equivalence
$env:LIFEWAR_BOARD_PROTOCOL='2'
npm run test:browser:live -- --playwright <Playwright目录> --executable <Chrome路径>
```

浏览器工具复用已安装环境，不下载依赖。原始结果在 `artifacts/performance/t13`；`tests/performance/summarize-protocol-v2.mjs` 会校验当前源码、性能记录与像素记录指纹一致后生成精简汇总。
