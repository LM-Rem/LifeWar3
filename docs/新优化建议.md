# 一、现状确认（我实测的）

| 项目 | 结果 |
|---|---|
| `npm test` | **146 通过 / 0 失败**，22.2s |
| `npm run benchmark`（本机） | 2,000 细胞 tick p50 **0.196ms**；11,792 细胞 p50 **0.544ms**；四阵营混战（D 峰值 2万）p50 **0.873ms**、p95 1.815ms、p99 3.698ms |
| `README` 历史数据 | 100k→12ms、300k→24ms、800k→56ms（单房间，不含浏览器/网络） |

**关键落差**：仓库自带的基准只跑到 ~2.4 万细胞量级，远低于文档反复记录的 50 万–100 万细胞密集场景（服务端 49–64ms、小地图 290ms）。也就是说**基准场景与实际失败场景脱节**——优化工作被"未覆盖的区间"卡住。

# 二、瓶颈分层定位

## A. 客户端渲染（当前最大的实际瓶颈）

**A1. 小地图全量重绘 —— 约 290ms/次，是密集场景的死亡源头**

```js
// public/renderer.js:318-336
if (this.full || this.dirty.size > this.side ** 2 / 2 || work > field.cells.size) {
  c.drawImage(this.background, 0, 0);
  if (field.state) { for (const [key, owner] of field.cells) paintCell(c, key, owner); ... }
```

`field.cells` 是一个最多 100 万条目的 JS `Map`，全量路径对每个细胞调用一次 `fillRect`。文档记录的 80 万细胞场景 Canvas 提交 **259.8ms**、端到端 **400.7ms**。而它每 33ms 被调用一次：

```js
// public/renderer.js:190
if(now-(this.lastMini||0)>33){this.drawMinimap();...}
```

**后果链**（已被 `docs/performance/2026-09-25-scheduler-minimap.md` 诊断证实）：小地图长帧（401.8ms）→ RAF 阻塞 → 收包积压 → 队列峰值 8（门槛 2）→ 触发恢复 → 3.2MB 快照 → 更慢。所有"密集场景未通过验收"基本都源于这一条。

**A2. 严格像素等价把优化空间锁死了**

`minimap-cache.js` 为保持 1×1 分数矩形 + 0.65 透明度的逐次合成语义，被迫保留逐格 `fillRect` 与插入顺序。三次尝试（路径批绘 / 透明分层 / `willReadFrequently`）均因像素差异被否。这是**目标定义问题**，不是实现问题——建议把小地图拆成"精确模式（测试用）"与"性能模式（DPR/降频/ImageData 直写）"，用设置开关隔离，而不是让性能模式永远被像素门槛否决。

**A3. 每帧的 `JSON.stringify` 签名计算**

```js
// public/renderer.js:118
const signature=JSON.stringify([x,y,this.boardRevision,this.me,this.baseHitRadius,this.playerCells,this.state?.status,this.state?.players,this.state?.nodes.map(n=>n.owner),this.extraLand]);
```

`placement()` 每帧（60Hz）序列化完整的 players 数组。同理 `minimap-cache.js:44-45` 每帧做**两次** `JSON.stringify`。这些可以用标量指纹（boardRevision + generation + 能量 + 指针坐标）替代。

**A4. `cells` Map 的内存与迭代成本**：100 万条 Map 在 V8 上就是几十 MB，`minimapCache.beginPacket` 还要为它建贡献者索引（每个细胞插入最多 9 个 Set）。`board` 已是 `Uint8Array`，Map 实际只服务于"插入顺序"这一个约束。

## B. 传输与恢复（第二瓶颈，且是架构性的）

**B1. 丢一代就退化成全量快照** —— 这是最值得改的一处

```js
// public/generation-queue.js:37
if(generation>this.received+1){this.fail('generation-gap');return false;}
```

任何一次迟到/积压/背压跳过 → 请求 `needsSnapshot` → 服务端发送 `alive.length × 4` 字节（100 万细胞 = **3.2MB**）→ 客户端 `cells.clear() + board.fill(0) + texture.reset() + minimapCache.invalidate()`。文档记录 P04 场景每轮触发 84–103 次恢复。

**建议**：服务端为每个连接维护最近 K 代变更的环形缓冲，gap 时发送**合并增量**（last-write-wins 并集，复用 `CellChanges` 已有语义），而不是全量快照。这能把恢复成本从 3.2MB 降到几十 KB，直接切断 A1 引发的恶性循环。这是我眼下单点收益最高的改动。

**B2. 协议 v2 已实现但未晋级**：包大小降 25%–68.3%，却因编解码 CPU 上升默认仍是 v1，且它在 P04 上**比 v1 更慢**（94.61 vs 75.55ms）。建议先做 B1，再重评 v2——带宽不再是密集场景的主要矛盾，Map 应用才是。

**B3. 无压缩的静态资源**：`public/patterns.json` **1.8MB**，每次进入对局 `fetch` 全量加载（app.js:896），服务端 `Cache-Control: no-cache` 且无 ETag、无 gzip。局域网无感，Ngrok 公网首屏很痛。加 `zlib` + ETag 是低成本高收益。

## C. 服务端模拟（稳态预算被吃掉的固定开销）

**C1. 每代两次 1MB 级别的内存操作**

```js
// src/evolution/backend.js:23
next.fill(0);                                   // 1,000,000 字节
// src/dormancy.js:60
this.snapshots[this.tick%this.snapshots.length].set(game.board);  // 1,000,000 字节
```

20Hz 下稳态 **40MB/s 的 memcpy**，与细胞数无关、纯属固定税。`next.fill(0)` 完全可以在 `commitEvolution` 的候选遍历里顺手清零（next 只会在候选位被写）；休眠快照可改为"仅当存在接近阈值的瓦片时才拷贝"。两者都是低风险改动。

**C2. 稀疏演化的随机访存**

`sparseCandidates` 每代对 `counts`(1MB) / `votes`(2MB) / `marks`(4MB) 做 ~9×alive 次随机访问。80 万细胞 = 720 万次/代 × 20Hz，7MB 工作集远超 L2，**cache miss 才是真正的墙**，不是 JS 本身。两条路：
- 把 `marks` 从 `Uint32Array` 降为 `Uint16Array`（代戳取模 + 环绕时重填），访存减半；
- **按 tile 分块处理**（如 128×128），让工作集落进 L2——这是经典 blocking 优化，潜在收益最大，但改动面也最大。

顺带：每活细胞一次 `key % size` 与 `Math.floor(key / size)`，`size` 是属性而非常量，V8 生成的是通用整数除法。可换 `Math.imul` 倒数乘法。

**C3. 领地索引的一次性 2000 万次计算**

```js
// public/territory.js:67-74
for(let key=0;key<grid.length;key++){ ... for(let i=0;i<territories.length;i++){ ... } }
```

1e6 × 20 站点，懒触发（第 512 次查询后）→ 首次大部署时主线程 ~100ms 卡顿，且服务端与每个客户端各算一遍。可在开局时算一次随 `state` 下发，或分片构建。

**C4. `adjacentNeutralTerritories` 是 O(T²×顶点²)**（territory.js:109-114），约 4 万次 `Math.hypot`，每次带 `neutralDeploy` 增益的部署都会触发，客户端 5Hz 的 `setState` 也会触发。应缓存。

## D. 服务端架构与健壮性

**D1. 单线程串行 tick —— 一个异常会永久停掉整个服务器**

```js
// src/tick-scheduler.js:19-35
callback();        // 这里抛出 → 后面的 arm() 永不执行
const end = now();
...
arm();
```

`createServer` 的 tick 回调里没有 try/catch：任一房间抛错（含 6 个房间共享循环）都会让**所有房间停止演化且无日志、无恢复**。必须加隔离 try/catch（按房间捕获 + 记录）。

**D2. 全部房间共用一个事件循环**：6 房间 × 20Hz 密集对局在单线程上必然互相拖累，且慢房间会阻塞所有 WebSocket 收发。中长期应把 `Game` 移入 `worker_threads`（每房间一 worker 或按负载分片），主线程只做 I/O。

**D3. 每房间固定预分配约 39MB**：`board/next/counts/votes/marks/candidates` + 双 `OrderedCells` + `CellChanges` + 9 张休眠快照，全部按 1e6 长度一次性开出（实测单房间 external 41MB）。小对局也照付，6 房间就是 ~234MB。可改为按需增长。

**D4. 无自适应降级**：服务端永远按 `hz` 发代，客户端跟不上就走 B1 的昂贵恢复。应加入按连接的自适应发代频率（慢客户端合并 2–3 代变更再发），而不是二选一"全量 or 快照"。

**D5. `/api/library` 搜索每次全量递归 `readdir` 3584 个文件**（server.js:21-32），无索引、无缓存。加一个启动时构建 + `fs.watch` 维护的内存索引即可。

**D6. `/api/patterns` POST 无鉴权**：公网（Ngrok）暴露时，任何人都能增删改 `patterns.json`；且并发 POST 是 read-modify-write，存在丢失更新与写坏文件的风险（无原子写、无锁、无条目数上限）。

## E. 代码质量与可维护性

- **`public/app.js` 78KB / 1330 行单文件**，混装页面、联机、输入、卡牌 UI、图案实验室；`onMessage` 巨型 switch；存在 ~900 字符的单行语句。已到必须拆模块的程度。
- **每帧 DOM 读写**：`onPreview`（app.js:1168）/ `onPresented`（app.js:734）每帧 `querySelector` + 写 DOM，无脏检查、无引用缓存；`positionBattleNotices` 每次 state 触发 3 次 `getBoundingClientRect()`（强制同步布局）。
- **图案编辑器 `drawEditor`** 在每次 `pointermove` 全量重绘，并对每个细胞做 `cell.split(',').map(Number)`（≤4096 次字符串解析）。
- **内存只增不减**：`eventIds` Set 只在开局清空（app.js:1001）；两个 `setInterval` 从不清理；rAF / ResizeObserver 无停止路径。
- **魔法数字 28**（核心保护半径）散落在 engine.js:110/330/399 与 renderer.js:133/161，不是常量。
- **硬编码 1000**：`renderer.js` / `minimap-cache.js` 直接写死棋盘边长，与 `config.json` 的 `size` 事实上脱钩。
- **冻结基线副本散落**：`tests/reference/`、`tests/baselines/t06|t12|t13/` 存有 `app.js`/`engine.js`/`renderer.js` 的完整拷贝，源码演进后维护成本会持续累积。
- **死配置**：`disconnectGenerations` / `roomIdleGenerations` 已不被读取，仅文档标注"保留字段"。

# 三、建议优先级

| 优先级 | 动作 | 预期收益 | 风险 |
|---|---|---|---|
| **P0** | tick 回调按房间 try/catch 隔离 | 消除"一错全停" | 极低 |
| **P0** | 增量合并恢复替代全量快照（B1） | 恢复流量 3.2MB→数十 KB，切断恶性循环 | 中（需保持顺序语义） |
| **P0** | 小地图拆"精确/性能"双模式 + 自适应降频 | 解开 290ms 长帧死结 | 中（需重定义验收口径） |
| **P1** | 去掉 `next.fill(0)` 与休眠全量快照拷贝（C1） | 稳态省 40MB/s memcpy | 低 |
| **P1** | 静态资源 gzip + ETag；`patterns.json` 懒加载 | 公网首屏 1.8MB→几十 KB | 低 |
| **P1** | 消灭每帧 `JSON.stringify`（A3）与每帧 DOM 写 | 客户端帧时间直接下降 | 低 |
| **P1** | 领地索引提前构建/下发（C3）、`adjacentNeutral` 缓存（C4） | 消除首部署 ~100ms 卡顿 | 低 |
| **P2** | `marks` 降宽 + tile 分块演化（C2） | 密集演化主战场 | 高（需保序验证） |
| **P2** | `Game` 移入 worker_threads（D2） | 多房间并发、I/O 不被阻塞 | 高 |
| **P2** | 基准补齐 50 万–100 万细胞场景 | 让优化有可回归的度量 | 低 |
| **P2** | `app.js` 拆模块、清理无界容器与定时器 | 可维护性 + 长局内存 | 中 |
| **P3** | `/api/patterns` 鉴权与原子写、库搜索索引 | 公网安全 | 低 |

---

**一句话结论**：项目在正确性上很扎实（146 测试 + 像素级回归 + 冻结基线，工程素养高于一般同类项目），真正的瓶颈已经不再是"演化算法写得不够快"，而是**三个架构约束**——客户端小地图的像素等价要求锁死了渲染优化、丢代即全量快照锁死了传输优化、单线程串行 tick 锁死了并发与容错。这三条不改，继续做编解码和缓存微调（T05–T13 已证明）每轮只能拿到 20%–30% 且始终过不了 20Hz 门槛。
