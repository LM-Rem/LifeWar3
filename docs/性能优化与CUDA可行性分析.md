# 保持逐代演化和画面表现的性能优化与 CUDA 可行性分析

日期：2026-09-23。依据当前工作区代码，而非仅依据 README 或历史设计文档。此次只做阅读、基准测试与分析，没有修改游戏实现或规则。现有未提交修改保持原样。

## 结论

优化空间较大，优先级是：**消除无效全量遍历 → 休眠增量化 → 稀疏/密集/变化前沿算法选择 → 客户端绘制与网络编码 → 多房间隔离 → CUDA 原型验证**。客户端与网络工作可提前并行推进。

CUDA 技术上可行，本机也具备 NVIDIA GPU 和 CUDA 编译器；但只把 B/S 演化搬上 GPU，无法解决休眠扫描、JS 对象分配、打包、网络和小地图绘制。更有价值的最终方案是 GPU 常驻棋盘、批量完成逐代计算，再回传当代结果或增量。小规模对局保留 CPU 路径。

## 约束与现状

“不跳帧”需要分别约束三件事：

1. 每代都计算，规则、阵营、休眠、基地/节点、卡牌与 AI 行为保持一致。
2. 每代权威结果按序送达并展示，不用中间代合并、降低广播频率或快照跨代替换掩盖负载。
3. 相机、动效和 UI 继续按原有渲染节奏运行，保持颜色、透明度、线宽、缩放和层级。

当前服务器是 20Hz，一代总预算 50ms；浏览器主画面使用 requestAnimationFrame，小地图约 30Hz。60Hz 显示器的帧预算约 16.7ms。服务器循环串行处理所有房间，50ms 不是每个房间各自独享的预算。

现有实现本身不保证所有代都实际出现在屏幕上：连接积压超过 256KiB 后会跳过增量，随后快照恢复；浏览器也可能在一次绘制前收到并应用多代。服务器超时时没有补演化，主要表现为代速下降。不能把这些恢复机制当作满足严格不跳帧的优化。带宽或终端能力不足时，固定实时速度、零丢代展示、有限延迟无法无条件同时保证。

## CPU 算法与数据结构

### 1. 先消除两处没有必要的全量遍历

`src/engine.js:220`：resolveObjectives 每代都执行 alive.filter，即使没有任何细胞被基地清除。可以记录是否真的删除过细胞，无删除时保留列表；有删除时稳定地原地压缩。淘汰与净化也应避免重复过滤同一列表。

`src/dormancy.js:90`：即使没有任何瓦片需要清理，仍遍历所有活细胞计算瓦片号。只有 remove 中存在标记才进入清理扫描；进一步维护瓦片成员索引，可只检查到期瓦片。

这两项容易实现和验证，能减少数组分配与 GC。上表目标结算和休眠总时间不是全部可节省时间，不能直接把它们相加当收益。

### 2. 休眠指纹从 O(L) 重算改为按变化更新

scan 当前每代遍历全部活细胞，计算两个包含坐标和阵营的哈希，并更新观察瓦片。大块静物在这种实现中仍每代支付全量成本。

可以对每次 oldOwner→newOwner 更新维护：

- XOR 指纹：异或掉旧贡献，再异或新贡献。
- 加和指纹：减去旧贡献，加上新贡献，保持原有 uint32 溢出语义。
- 数量：按出生/死亡修正；纯阵营变化只改指纹。
- 瓦片边缘的 2 格重叠观察区：更新所有受影响观察瓦片。

保持每代处理 400 个瓦片的历史、周期、年龄与预警，把活细胞扫描变成变化格处理。大量静物、少量边缘扩张特别适合。

必须覆盖部署、播种、净化、出生、死亡、基地命中、淘汰、休眠删除等所有写路径。现有 changes Map 只保存最终 owner，并非可靠的逐阶段 old/new 日志。尤其当前休眠快照是在本代休眠删除前保存，改造必须维持这个时点，不能直接改成每代最终棋盘的历史。

先保留到期逐格精确校验，不能只凭哈希相等删除。9 份历史棋盘约占 9MB，但每代只复制其中 1 份，约 1MB/代、20MB/s/房间；不应把它误读为每代复制 9MB，也不应先为节省这部分带宽引入复杂压缩。进一步可按脏瓦片复制历史，但必须验证所有周期相位与环形槽复用。

### 3. 按候选覆盖率选择稀疏与密集演化

记 N=1,000,000，L=活细胞数，C=活细胞与其邻域的去重格数，D=变化数，R=局部规则数。

当前主要成本约为 O(8L+C+CR+D)，另有全图清零、全活细胞扫描。它已经是有效的稀疏算法，不应简单描述成“逐格扫描百万格”。但是在 C 接近 N 时，稀疏算法仍需 marks 检查、计数散写、候选列表和多遍访问，优势消失。

建议保留两条路径：

- 稀疏：沿用邻域候选方式，适合局部战斗。
- 密集：按行顺序读取旧棋盘，每格收集 8 邻居，寄存器累加总数和阵营票，直接写新棋盘和差异，减少散写与中间数组。

按 C/N、活跃瓦片比例和实测耗时决定切换阈值，并加滞回，避免来回切换；不预设“超过 10 万就必定更快”。更成熟的实现可按 32×32 或 64×64 瓦片混合处理。

当前配置禁止 B0，因此完全空且周围无活细胞的区域可以安全不参与当代演化；但 S0 合法，孤立活细胞必须保留在候选中。瓦片 halo 至少包含一格相邻输入，边界不环绕。

### 4. 按变化前沿更新，比按活细胞更新更适合静物海

维护持久邻居计数和阵营票数，只在某格出生、死亡或换阵营时更新周围 8 格，再重算受影响格及变化格自身。普通稳定区域由 O(L) 降到接近 O(D+受影响格数)，无需跳过任何一代的输出。

实现必须分阶段：从同一旧棋盘算出整代变化，再提交所有变化和邻居计数，不能边改棋盘边算下一格。全局规则和同化效果变化要使相关范围失效；局部规则生效/到期要激活覆盖区；外部操作、核心命中和休眠删除同样进入前沿。

最差 D 接近 N 时，维护前沿会比密集扫描贵，所以应保留密集退路。这比立即引入通用 HashLife 更适合当前有限棋盘、频繁交互和逐代可见的游戏。

### 5. 规则查询与内存分配

- B/S 集合可编译为 9 位掩码，用移位测试替换热循环 Set.has。
- 局部规则最多 8 个，当前每候选执行 findLast 和距离判断。规则变化时生成每格规则编号，或先按瓦片筛选；准确保留重叠时最后施放者优先。
- nextAlive 改为复用缓冲区和有效长度；删除使用稳定压缩，减少每代新数组。
- changes Map 可改成“脏标记 + 首次出现顺序的 key 缓冲 + 最终 owner”，保持同一格多次修改只打包最终值。
- packet 直接遍历 Map 写入预分配结果，不先展开成 entries 二维数组；快照同样避免 alive.map 创建大量二元数组。
- 不要未经测量就把 next.fill(0) 改成零散清除；连续内存清零通常便宜，稀疏清理还容易残留旧代细胞。

### 6. 固定几何预计算

基地/节点坐标固定，可预生成圆域格子索引，避免每代反复计算距离；先做这个简单优化，再决定是否需要按变化维护区域内阵营计数。占领进度仍须每代结算，即使接触阵营未变化。

Voronoi 固定，可以开局生成每个整格的分区编号表（当前分区数量可用一个字节表示），占领变化只改分区归属表。它主要改善大型部署、每帧预览和 AI 搜索，不是邻居演化的核心瓶颈。预计算必须使用现有站点顺序解决平票。

AI 的 filter(...).slice(0,64) 可以改成按原顺序收集满 64 个即停止；部署搜索顺序与成功退出条件保持不变。

## 客户端与网络：CUDA 不会代替这些优化

### 小地图

`public/renderer.js:249` 每次绘制遍历 this.cells，为每个活细胞发出 fillRect。80 万细胞、约 30Hz 对应约 2400 万次调用/秒，只是按代码计算的调用量，不是浏览器 FPS 实测。

建议缓存小地图的细胞层，通过变化格标记受影响的小地图像素区域；每次重建脏区域后照常合成节点、基地、领地和相机框。由于每个世界格画的是小地图上的 1×1 半透明矩形，可能覆盖相邻像素，脏区须扩张到完整覆盖范围，并裁剪重绘。

**不能直接用 drawImage(world) 缩小替代，也不能随意按阵营合并绘制。** 当前多个细胞会在小地图像素范围内重叠，顺序影响混色；缩小会改变密度、透明度和抗锯齿。严格保持画面时，必须维护原始贡献顺序，在脏区域内按原顺序重放，或构造经像素比对证明等价的合成方式。此项在大量变化时仍可能很贵，需要单独做浏览器原型。

### 主战场纹理与部署预览

updatePacket 目前对每个变化格调用 fillRect/clearRect。主战场离屏棋盘是整数格、一格一像素，可使用持久 ImageData/RGBA 数组批量写颜色，按脏矩形上传；变化密集时整张上传，稀疏时按瓦片或矩形合并上传。保持空格透明、原调色板与关闭平滑缩放。Canvas 与纹理后端仍应截图验证颜色和缩放边缘。

placement 每帧反复求图案边界、逐细胞查领地。可以缓存图案尺寸和依赖版本；只有指针对应格、图案、棋盘、能量/容量、领地、状态或卡牌效果变化时重算合法性。相机移动导致目标格改变也必须失效。预览绘制和动效仍每帧执行。

### 网络编码

现有增量为每格 4 字节，负载约 4D×20 字节/秒/客户端。高变化实测若维持 20Hz，仅细胞负载约 40MB/s/客户端，4 个客户端约 160MB/s 服务端出站，已超过千兆网理论 125MB/s，尚未算协议开销。

无损方案是逐代、按瓦片自适应选择稀疏索引或密集 owner 数据：完整字节棋盘 1MB，理论上变化超过 25 万格时就小于现有索引增量；5 种值用 3bit 可表示，整图理论为 375KB，但需计入标头、解码和编码成本。RLE 适合大片同色，杂乱棋盘未必有效。每个包仍对应同一代，不能以合并多代换吞吐。

采用密集编码不代表必须清空并重建客户端 Map；应更新现有结构并保留需要的插入/绘制顺序。否则棋盘内容一致也可能导致小地图混色不同。直接改用当前快照恢复机制会有这一差异。

## 多房间并发

服务器 setInterval 在同一 JS 线程串行处理所有房间，重房间会拖慢其他房间、消息处理和心跳。适合每房间或小规模房间组使用长期 worker，主线程负责连接和路由。只传命令、打包结果和必要状态，避免每代结构化克隆整套棋盘。

Node 官方将 worker_threads 定位为适合 CPU 密集型 JS 的工具，支持共享内存和转移 ArrayBuffer：[Worker threads](https://nodejs.org/download/release/latest-v22.x/docs/api/worker_threads.html)。这里首先获得的是房间隔离和多核吞吐，并不自动让一个房间的单代计算更快。异步化也必须明确命令进入哪一代，保持次序和权威判定。

## CUDA 路线

### 为什么适合

每格下一状态只依赖同一旧棋盘的 8 邻居及小规模规则参数，是适合并行的 stencil。建议一个线程负责一个输出格，读取邻居、计数、投票后只写自己的输出。不要直接照搬 CPU 的“活细胞向邻居散写”形式，否则容易引入原子加法竞争。

先实现按行合并访存的直接读取版本，再测 shared-memory tile + halo，不能假定共享内存一定更快。棋盘双缓冲约 2MB，休眠历史约 9MB，再加规则、差异和统计缓冲，基础工作集远低于本机显存容量；主要难点是同步和完整管线。

NVIDIA 官方建议优先评估热点、减少主机/设备数据往返并保持合并访存：[CUDA Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)。

### 分两步实施

**验证原型：** Node 通过异步原生扩展或长期 CUDA 子进程，将旧棋盘和规则传给 GPU，GPU 只做下一代，回传给现有 CPU 规则管线。棋盘每方向约 1MB、20Hz 合计约 40MB/s/房间，并不是数量级上无法承担；真正需要测的是桥接、复制、同步和 CPU 后处理。原型应和优化后的 CPU 比，不能只和旧 JS 比。

**长期方案：** 让棋盘和历史常驻显存。CPU 负责网络、命令排序、现实时间与卡牌参数；GPU 负责演化、接触区域统计、人口归约、休眠指纹/精确校验和差异生成。基地命中、淘汰与休眠清理按原顺序提交，返回当代差异和小规模统计。CPU 保留必要镜像用于部署、AI、重连；镜像必须在下一批命令校验前更新完整，不能用旧代数据批准部署。

管线阶段必须保留：效果到期/规则生效 → 演化 → 节点和基地结算/淘汰 → 休眠 → 能量/胜负/发牌。不要为了减少 kernel 次数而改变语义。

可用异步复制、页锁定缓冲和缓冲池重叠网络处理与设备工作；不要在 Node 主线程里同步等待长计算。跨代有真实依赖，不能假装任意多代可并行；也不能合并若干代后只返回最后一代。

### 保持一致性的难点

- 邻居票数、平票起点 key+generation、单方同化/多方抵消，用整数精确复现。
- 局部圆域、有限地图边界、局部规则覆盖顺序与 S0 必须一致。
- 休眠双哈希使用相同整数溢出语义，到期仍精确比较；保留快照与清理时点。
- 多基地同时受伤、节点压制现实秒结算、护盾有效区间不能被拆成不同语义。
- GPU 压缩输出通常会重排活细胞。当前 AI 取 alive 中前 64 个敌格，重排可能直接改变 AI 行为；客户端 Map 顺序也可能改变小地图叠色。严格行为一致需要保留原顺序或建立等价的顺序索引，这可能抵消部分收益，必须纳入原型成本。
- 现实时间在当前代码中多处读取。等价测试应注入同一时钟和命令序列；把所有时间读取合成一次 tick 时间是潜在语义调整，应单独决定，不能悄悄混入优化。

### 收益边界与可移植性

密集扩张实测约 61.56ms，其中其余 step 为 35.78ms。即使这部分全部变成零，目标结算、休眠、打包仍约 25.78ms；这是只替换这部分的理想上限示例，而实际 GPU 还要付桥接和同步成本。高变化场景仅休眠、目标结算与打包就约 47.4ms，几乎耗尽 50ms。必须按端到端时延评估。

CUDA 适用于服务器上支持 CUDA 的 NVIDIA GPU。其他玩家继续用现有浏览器，不要求他们安装 CUDA。它会增加 Windows 原生构建、运行库、版本兼容与发布维护成本；工具链要求参见 [NVIDIA Windows 安装指南](https://docs.nvidia.com/cuda/cuda-installation-guide-microsoft-windows/index.html)。CPU 回退应保留，GPU 故障恢复需从已确认棋盘和命令位置继续，不能静默重开或跳代。

浏览器端跨厂商 GPU 计算可考虑 WebGPU，但这会涉及另一套部署与架构，不是给现有权威 Node 服务器打开 CUDA 开关。浏览器能力与安全上下文条件参见 [WebGPU API](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API)。服务端跨硬件需求也可先比较原生 CPU/SIMD 路线。

不建议第一步引入 FP16、Tensor Core 或复杂 HashLife：本项目是小整数邻居逻辑，多阵营、逐代交互和规则变化使它与矩阵乘法或跨大量代跳跃的典型收益场景不同。位并行/SIMD 可以进一步研究，但须同时承担四阵营计数，不能只拿单色生命游戏速度外推。

## 推荐实施与验收

| 优先级 | 工作 | 预期作用 | 主要风险 |
|---|---|---|---|
| P0 | 全链路测量，区分 L/C/D | 找到真实场景瓶颈 | 短基准与实战差异 |
| P1 | 无删除不扫描，稳定压缩，直接打包 | 减少 CPU 遍历/GC | alive/变化顺序 |
| P1 | 休眠指纹增量维护 | 降低大量静物成本 | 历史时点与遗漏写路径 |
| P1 | 主纹理批量更新、小地图脏区缓存 | 减少浏览器调用量 | 透明叠色/抗锯齿一致性 |
| P2 | 稀疏/密集切换、规则索引 | 改善高覆盖率演化 | 阈值与候选顺序 |
| P2 | 逐代自适应无损协议 | 降低高变化带宽 | 解码与顺序保留 |
| P2 | 多房间 worker 隔离 | 提高并发吞吐 | 命令/状态同步 |
| P3 | 变化前沿、CUDA 对照原型 | 获得更大算法/硬件收益 | 实现复杂度与一致性 |

验收不仅比较最终棋盘：使用固定随机源、注入时钟和同一操作日志，逐代比较棋盘、人口、节点、基地、能量、卡牌、休眠年龄/预警、AI 选择及增量重建。覆盖所有法则、边缘、局部重叠、净化、淘汰、周期 1–8、跨瓦片飞船、同时核心毁灭以及规则切换。

浏览器在固定相机、DPR、缩放和时间下截图比对，特别验证小地图混色、死细胞透明度和动画。性能测量包含命令等待、演化、休眠、打包、发送、客户端解码/绘制及多房间 p95/p99；至少分静物密集、局部稀疏、高变化、到期批量清理和多房间场景。目标是在 50ms 服务端代预算与目标显示器帧预算内留出余量，而非只报告 kernel 均值。
