# 窄带网络优化实施计划

以本次用户需求为准：保留启动默认 GPU＋v2，逐代计算、逐代传输，不合并代数；建议文档仅为待评估输入。

## 本轮实施

1. v2 增加显式协商的有序坐标差值变长编码，保持 owner、插入顺序、快照、代数与 epoch。逐包比较完整长度，只在更小时使用；旧客户端继续原 v2。覆盖负差值、大跳跃、越界、重复、截断、过长 varint、历史重放与混合客户端。测量真实 socket 字节和 CPU，而非仅估算。
2. placement 改依赖值比较，去掉每帧 JSON.stringify；对原地状态更新仍正确失效。几何邻接关系缓存、领地索引按需分行构建，避免首次大部署同步构建百万格；不把额外全图索引传到公网。
3. 清理小地图空钩子和逐格绘制死参。主图保留像素等价回归，小地图单独检查空间分布、状态变化、尺寸、清空/重连，不用旧像素要求阻止近似优化。
4. 常规 benchmark 增加持续50万细胞高变化档；写清历史默认值与现行GPU＋v2的区别。

## 暂不实施及理由

- 已完成的房间隔离、逐代重放、静态 gzip、类型数组存储保留。
- 改 GPU＋v1：拒绝，带宽是当前实际约束。
- 合并多代：拒绝，不能以牺牲逐代过程换带宽。
- next.fill(0) 改逐候选清零：不是纯收益；稀疏清零必须清理交换缓冲中的旧活细胞，密集时随机写可能慢于连续清零。当前不贸然修改。
- 休眠快照按需复制：历史不足会影响周期精确校验，不属于低风险优化，保留完整历史。
- marks 降宽、tile 分块：先验证编码和实际网络收益，暂不同时改CPU演化核心。
- 房间 worker：有价值，但涉及命令边界、计时、状态发布与GPU调度的大范围迁移，留作独立阶段。
- app.js 整体拆分：与本轮带宽目标关系较弱，暂缓。
- 图案库搜索索引：影响库搜索而非对战，暂缓。
- 图案管理鉴权/原子写：对公网有价值，当前无鉴权写接口仍是已知问题；需要独立明确本机与远程管理流程，本轮不混入协议优化。结果文档明确保留风险，不将其标记为已修复。
- 原生GPU资源泄漏：已采用有界等待和停用设备，本轮不尝试强制终止原生worker；驱动永久挂起仍可能保留资源，不能声称已彻底解决。

## 验证

定向协议、混合联机、缓存与空间查询测试；完整 npm test 与逐阶段回放；实际浏览器主图像素对照、小地图语义验证、GPU＋v2全链路。基准比较相同代数和状态，记录socket字节、包尺寸、编解码耗时、缺代与恢复。保留全部结果与失败限制。
