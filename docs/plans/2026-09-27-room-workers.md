# 房间线程隔离实施计划

目标：GPU同步等待、CPU演化/结算和棋盘编码不再阻塞WebSocket主线程；高负载房间不阻塞另一房间的选卡。保持每代完整结算、逐代协议、卡牌隐私、断线重连与权威命令顺序。

## 设计决策

采用每房间一个Node worker，内部继续使用现有同步Game与GPU桥接；主线程只持有大厅成员、连接和房间状态摘要。仅将GPU等待改异步不能隔离CPU结算和编码；每个tick往返整个Game会增加复制且破坏类实例，因此不采用这两种方案。

房间worker独占Game、调度器、GPU实例、编码基准和32代/16MiB历史。部署/卡牌/离线命令经消息端口FIFO，在完整tick之间处理。每个玩家连接带会话序号，过时输出不能投递到后来重连的连接。主线程不读写worker棋盘。对局epoch隔离重赛。

棋盘输出最多一个未确认批次；主线程发送后回报缓冲量。慢连接从worker历史逐代重放，超限明确快照恢复。输出ArrayBuffer复制一份后transfer，保留历史不被detach；相同包在同批次共享。控制回执单独发布，不等待棋盘批次确认。命令设置有界在途数，拒绝过载，不自动重放未知结果。

房间启动异步；设备不可用仍在房间线程内回退CPU。异常房间停止，不自动迁移半结算状态。房间销毁、重赛、空房过期、关服均关闭worker；普通断线保留90秒恢复窗口并继续演化。GPU原生关闭采用有界等待和unref，不强制终止可能处于Dawn中的线程。

实测补充：高负载下立即开始下一代会让刚收到候选的选卡请求多等待一代。仅在在线真人仍需选牌、且下一代已经超期时留2ms命令处理窗口；其他调度不变。需要同时记录选卡延迟和演化吞吐，不以跨房间收益掩盖同房间退化。

## 实施步骤

1. 新建 `src/room-runtime.js`：封装命令、成员生命周期、tick、快照/历史与输出窗口，直接单元测试与Game对照。
2. 新建 `src/room-worker.js` 与 `src/room-worker-client.js`：启动、消息、转移缓冲、有界命令、故障和关闭协议。
3. 修改 `src/server.js`：接入worker路径，保留显式inline回退；主线程不执行worker房间Game方法。运行脚本默认启用 `LIFEWAR_ROOM_WORKERS=1`，直接导入createServer保持原基准默认。
4. 测试真实worker联机、部署/选卡/出牌、隐私、重连、慢连接历史、结束/重赛、异常隔离、退出清理；CPU逐代对照和硬件GPU回放。
5. 测量同条件inline/worker下的主线程延迟及另一房间操作延迟，保留测试条件与不稳定结果；更新README和结果文档。

## 验收与边界

必须有真实worker路径测试，不能只依赖inline旧测试。单房间吞吐提升不是必要条件；重点是连接响应和房间互不阻塞。共享CPU/GPU/物理带宽仍可能竞争，同一繁忙房间的操作仍需等待当前代完成。线程增加每房间内存和GPU实例开销，最多6房间限制不变。不通过合并代数或伪造选卡确认改善数据。
