## 1. 成功条件与范围

### 1.1 必须保留的行为

| 方面 | 不允许改变的内容 |
|---|---|
| 演化 | 1000×1000、有界不环绕、每代完整 B/S 更新、S0 支持、B0 禁止 |
| 阵营 | 存活保留阵营；新生多数票；平票以 key+generation 决定；同化冲突规则 |
| 规则覆盖 | 全局预告与生效时点、局部最后施放者优先、到期恢复 |
| 目标 | 先节点及核心相关结算，再统一淘汰；护盾仍消耗接触敌细胞；同时毁灭可平局 |
| 休眠 | 每代历史、周期、年龄、阈值衰减、预警、精确复核、熵减和删除时点 |
| 操作 | 部署原子性、能量、容量、范围、净化、播种、卡牌实例与顺序 |
| AI | 决策频率、候选目标顺序、尝试次序、随机数消耗次序 |
| 网络 | 权威验证、隐私、重连、增量可重建、状态推送约 5Hz |
| 视觉 | 调色板、透明度、图层、格线、受击圈、领地虚线、字体、动效、相机、触屏操作 |

不以减少地图大小、细胞数量、模拟频率、广播频率、主画面刷新频率、小地图刷新频率、DPR、粒子或动效来获取收益。不改变休眠清理代数，不把多个代合成一个最终状态。

### 1.2 “不跳帧”的可验证定义

为每局使用 `roomEpoch + generation` 标识代；为命令与状态另设序号。每个前台客户端分别记录：

- `computedGeneration`：服务端完成的代。
- `sentGeneration`：该连接实际提交发送的代。
- `receivedGeneration`：客户端完整接收的代。
- `appliedGeneration`：客户端应用完变化的代。
- `drawnGeneration`：该代主战场被提交到 Canvas 的代。

正常持续连接下，每条序列都必须连续，且每个收到的代至少单独参与一次主战场绘制；不得在一次绘制前把几代覆盖成最后一代。空变化包也有代号，仍需记录该代。初始化快照不算漏代。

requestAnimationFrame 只能证明绘制提交，不能单独证明显示器实际扫描输出。自动化以代序列与浏览器合成 trace 为证据；需要证明物理显示效果时，增加外部高帧率录像。报告不得把 rAF 回调数直接叫作“真实呈现帧数”。

断线、后台标签节流、系统挂起、设备故障及带宽低于需求时，单独记录“脱离实时能力范围”。保留现有快照恢复以恢复可玩性，但凡测试期间触发跨代恢复，该段严格不跳代验收失败，不可计入成功样本。不得无限堆积所有历史来伪造连续性。

### 1.3 目标运行范围

第一版验收默认如下，全部是目标，不是现有性能承诺：

- 服务端参考机：i9-13900HX，固定电源模式，Node v24.11.1；GPU 实验使用本机 RTX 5070 Ti Laptop GPU。
- 主验收网络：实测可用带宽的千兆有线 LAN，RTT≤5ms；四个前台客户端。
- 主验收客户端：桌面 Chromium 系浏览器，1920×1080，60Hz，DPR=1 与 2 分别测，记录实际 GPU；明确服务器与浏览器是否同机。
- 普通场景：单房间与六房间分别验收。密集/高变化场景：先承诺单房间，六房间作为容量边界测量，不能未测试就宣称支持六个满载房间。
- 手机、Wi-Fi、公网隧道及 120/144Hz 显示器做兼容性/扩展性能矩阵，单独出结论，不以桌面结果替代。

### 1.4 性能与资源门槛

| 指标 | 主验收目标 | 说明 |
|---|---|---|
| 单房间服务端完整 tick | p95≤25ms，p99≤40ms | 含规则、休眠、打包和提交发送；不含网络传播 |
| 服务端 50ms 截止期 | 认证运行中超期次数为 0 | 报告最坏值；只有 p99 合格不能称零超期 |
| 实际代速 | 长时约 20 代/秒，无持续落后 | 同时报告各 1s/10s 窗口及累计 schedule lag |
| 客户端每帧工作 | p95≤8ms，p99≤12ms | 解码/应用/主地图/小地图/UI 分项；60Hz 目标 |
| rAF 间隔 | p99≤25ms；>33.3ms 异常逐项审查 | rAF 非物理显示证明；不能忽略长任务 |
| 呈现队列 | 正常≤2 代，无持续增长 | 一旦跨代丢弃，严格验收失败 |
| 命令接收至权威处理 | LAN p95≤75ms，p99≤150ms | 不含原有卡牌消散动画、法则预告 |
| 权威提交至客户端绘制提交 | LAN p95≤75ms，p99≤150ms | 跨机需校准时钟与误差；无校准只报告本机分段 |
| 棋盘、规则、顺序差异 | 0 | 任何性能提升均不能抵消一致性失败 |
| 正常局内丢代/跨代快照 | 0 | 断线恢复另项验证 |
| 网络利用率 | 负载≤实测可用带宽的 70% | 按实际客户端数合计，不只看单客户端 |
| 内存 | 热身后不持续增长 | 运行 30min/2h 趋势；释放房间后回到稳定平台 |

内存以 RSS、heapUsed、external、arrayBuffers、GPU 显存分别报告，避免只看 JS heap。首轮建立各场景内存上限；同场景较基线增长超过 25% 时必须解释具体持久缓冲，不能自动通过。1KB/代等持续正增长即使尚未耗尽内存，也应分析。

## 2. 基线、方案选择与里程碑

### 2.1 已知基线

前轮已有 81 项测试通过。原 expansion 基准 10万/30万/80万初始细胞平均约 11/24/58ms。四阵营预热压力实验中，密集扩张平均 61.56ms，高变化平均 117.61ms。详细条件见前期分析。

这些短测值只作定位参考，不是本方案的正式基线。执行时重新记录源文件哈希、规则和运行环境；不可直接以 HEAD 代表当前基线，因为工作区已有未提交改动及未跟踪文件。

### 2.2 选择的路线

| 路线 | 决定 | 原因 |
|---|---|---|
| 先改 CPU 数据流与绘制，再评估 CUDA | 采用 | 能直接处理已测热点，保留兼容性，便于逐项归因 |
| 直接全面 CUDA 化 | 暂不采用 | 休眠、规则、顺序和网络未隔离，难验证端到端收益 |
| 降频、抽帧、合代或降低画质 | 排除 | 不符合用户约束 |

### 2.3 阶段依赖

```text
M0 基线/参考实现/追踪
 └─ M1 低风险 CPU 优化与有序数据结构
     ├─ M2 休眠增量化、几何/规则缓存
     ├─ M3 主纹理、小地图、部署预览、逐代绘制
     └─ M4 稀疏/密集后端、变化前沿实验
M0 + M1 + M3 ─ M5 无损自适应协议
M0 + M1 ─ M6 多房间 worker
M2 + M4 + M5 ─ M7 CUDA 对照原型与可选常驻化
全部拟交付项 ─ M8 综合认证、灰度和文档
```

M3 与 M2 在技术上可独立推进，但本文不自动创建并行任务或授权代理调度。任何阶段可因无收益停止，而不阻碍已验证优化交付。

## 3. 测试基础与统一契约

### 3.1 参考实现

新增 `tests/reference/`，保存优化前引擎、休眠、AI、规则配置及其依赖的冻结副本；保持目录关系，使导入始终指向副本。浏览器参考实现也保存 renderer 及共享几何依赖。新增 `tests/reference/manifest.json`，记录每个文件 SHA-256、配置快照、来源日期和工作区状态。

参考实现禁止回引优化后的生产模块。不能一边优化，一边为让对比通过而修改参考算法。若发现原有 bug，独立记录并决定是否修复；性能分支不悄悄改变基线规则。

测试允许两边注入同一伪随机源和时钟。`Game.event()` 中直接读取 Date.now 的地方也需要控制：使用测试进程时钟适配/模拟，或分别记录事件时间并验证时间源，不可把业务时间差异全部忽略。时间在语义阶段边界推进，不按实际测试耗时推进。

既有单元测试直接写 board/alive；引入增量索引后必须增加测试专用 `loadFixtureState`/`rebuildDerivedState`，在种子写入完成后一次性重建索引。生产命令不得绕过变更入口。不能用每代全量重建补救遗漏索引。

### 3.2 回放格式与证据

新增 `tests/helpers/replay.js`，支持以下记录结构：

```js
// 拟定格式；毫秒相对于本局 startedAt，phase 限定命令屏障位置。
{
  seed: 91,
  rulesFixture: 'production-20hz',
  initialStateFile: 'dense-growth.bin',
  operations: [
    { seq: 1, generation: 20, phase: 'beforeStep', atMs: 1000,
      action: 'deploy', playerId: 1, x: 200, y: 200, cells: [[0, 0]] }
  ]
}
```

每代比较：board 所有字节、有效 alive 顺序、changes 的 key/owner 及首次插入顺序、players、nodes、status/winner、卡牌/规则状态、休眠指纹/历史/period/age/warnings，以及随机状态。传输后比较客户端棋盘与有序渲染贡献，不只比较最终棋盘。

失败保存：seed、操作日志、第一处分歧的阶段/代/格子、参考与目标前后棋盘、相关区域规则、随机源位置。运行摘要哈希只用于快速定位；正式正确性测试必须直接比较，不以哈希相等代替完整比较。

禁止在正式性能计时区间执行参考引擎、逐格比较、截图、逐格日志或测试断言。正确性和吞吐测试使用同一夹具，但分开运行。

### 3.3 变更与顺序契约

新增 `src/cell-changes.js`，区分两个用途：

1. **阶段变更**：包含 key、oldOwner、newOwner、phase，驱动邻居索引、休眠指纹、人口及区域计数。
2. **网络最终变更**：同一格在广播间隔内可多次写入，保持第一次写入顺序，只保留最终 owner，复现当前 Map 语义。

关键示例：本代部署某格、演化将其杀死，网络最终值为 0，但阶段日志不能丢掉出生与死亡对缓存失效的影响。纯阵营变化必须更新阵营票，不能当作“活死没变”忽略。

建议使用平行类型数组和有效长度表达批次，避免为每个变化创建对象；语义接口如下：

```js
// 仅表示契约，不要求生产热循环逐格调用该 JS 方法。
recordTransition(key, oldOwner, newOwner, phase);
recordNetworkFinal(key, newOwner); // first-touch order, last value
finishPhase(phase);
```

批量演化必须从旧棋盘算完整结果，再提交；不允许更新一个格子后把新值作为另一个格子的本代邻居输入。

### 3.4 后端契约与功能开关

拟新增内部后端接口 `src/evolution/backend.js`：

```js
// 语义接口；CPU 可同步返回，worker/CUDA 通过统一适配器异步返回。
evolve({ board, aliveKeys, aliveLength, generation, rules, priorityOwner });
// -> { nextBoard, nextAliveKeys, nextAliveLength, ownerTotals, transitions }
```

CPU 优化阶段保留现有 Game.step 的同步调用方式；在 worker/CUDA 集成阶段再增加异步调度适配器，不提前把所有调用 Promise 化。归属平票的 generation 必须是当前 step 已递增后的值。

拟新增 `src/performance-config.js`；开关仅供开发、测试和灰度，不混入 `config.json` 的游戏平衡数值：

- `LIFEWAR_EVOLUTION=legacy|sparse|dense|frontier|auto|cuda`
- `LIFEWAR_DORMANCY=legacy|incremental`
- `LIFEWAR_ROOM_EXECUTION=main|worker`
- `LIFEWAR_PROTOCOL=v1|v2|auto`
- 浏览器测试参数 `renderer=legacy|cached`、`trace=1`，生产默认不暴露诊断面板。

每次记录实际生效路径、切换次数与理由。未验证路径默认关闭；不得请求 cuda 后静默使用 CPU 并仍标注 CUDA 成绩。

## 6. 测量方法与统计

### 6.1 快测、完整测与发布测

| 等级 | 正确性 | 性能 | 适用 |
|---|---|---|---|
| 快测 | 原测试+受影响模块+固定 5 种子×200代 | 受影响场景预热后 300 代，3 轮 | 每项实现期间 |
| 完整测 | 20 种子×1000代；高风险增量至少一组10000代 | 100 代预热，1000 代测量，5 轮 | 算法/协议/后端完成 |
| 发布测 | 全矩阵、组合开关、故障回放 | 真实20Hz运行≥30min，关键组合2h | 最终默认配置 |

完整逐格比较可能昂贵，允许离线跑完，但不能用降低比较精度替代。性能预热可在同构副本上执行；正式 A/B 必须从相同预热后的状态开始，不让 A 测开局而 B 测已衰减的后期。

### 6.2 A/B 规则

1. 基线与目标使用相同配置/种子/命令；同一时段交替 A/B，再交换顺序，避免温控和缓存偏差。
2. 性能运行串行进行，不同时跑 npm test、其他 benchmark、视频编码或后台 GPU 任务。
3. 报告每轮 p50/p95/p99/max 和超期次数，再报告跨轮中位数；不要平均不同分布的 p99 后当全局 p99。
4. 改进定义为 `(baseline-candidate)/baseline`，同时给绝对毫秒。跨轮波动大于收益时结论为“不确定”，增加重复或不采纳。
5. 普通场景 p95 稳定回退超过 5% 时必须解释；可通过关闭该场景的优化保留总体收益。
6. 正式性能模式不强制 GC；可单独诊断 GC，但不得剔除自然 GC 长尾。CPU/GPU/内存统计都应包括预分配后稳态与冷启动。
7. 日志保留异常代和失败运行，不能只选最快一轮。

### 6.3 端到端时钟

同机使用单调时钟测分段，不把 Date.now 的系统校时当延迟。跨机先用多次往返估计偏移/误差，或使用部署环境的时钟同步；记录估计误差。若误差过大，只报告 RTT、服务端耗时和客户端本地排队，不输出虚假的精确单向时延。

记录单代的 traceId，使服务端阶段、包、客户端应用和 draw 可关联。GPU events 只用于设备阶段；CPU 总时延必须包含排队、同步和拷贝。计算出错或回退必须在 backendUsed 中体现。

`artifacts/performance/<run-id>/` 保存运行清单、JSONL 样本、汇总、失败回放、浏览器 trace 和截图差异；大文件不默认进入 Git，可提交小型摘要及复现夹具。原始命令日志不含会话令牌或外部用户隐私。

runner 必须在导入 src/config.js/engine.js 之前选择 `LIFEWAR_CONFIG_PATH`，必要时启动子进程；不能在 ES module 已缓存 RULES 后改环境变量并以为配置生效。性能夹具不得覆盖用户 config.json。

## 8. 回退、灰度与验收决策

### 8.1 每阶段回退

| 优化 | 回退方式 | 限制 |
|---|---|---|
| 无效扫描/直接打包 | 回退独立提交 | 无协议变更 |
| 增量休眠 | 启动时选 legacy；运行中切换须重建当前指纹并保留历史 | 不能清空年龄冒充恢复 |
| sparse/dense/frontier | 在代边界切换并初始化派生缓存 | 保持棋盘、顺序、generation |
| 绘制缓存 | 重建 legacy 离屏图与有序细胞状态 | 不能跳过待展示代 |
| v2 协议 | 新连接协商 v1；已有连接切换需明确代边界 | 不能把 v2 密集包误按 v1 解码 |
| worker | 新房间选 main；运行中不强迁移，除非完整状态迁移已验证 | 不允许丢命令 |
| CUDA | 由完整 checkpoint+日志恢复到 CPU 或新房间选 CPU | 不能仅复制当前 board |

### 8.2 灰度顺序

1. 测试环境全部对照通过。
2. 本机训练房间开启一个新开关，记录完整局，再增加交付组合。
3. 局域网四人前台对局至少 30 分钟，覆盖强力卡牌与节点压制。
4. 目标客户端/房间组合长期测试。
5. 只有明确通过的路径成为默认；无 CUDA 机器继续使用 CPU。

灰度不使用隐藏的抽帧、自适应画质或不记录的 CPU 回退。实时对局发生任何 board/顺序/隐私错误，立即停止扩大范围并保留首错日志。

### 8.3 CUDA 采用决策表

| 结果 | 决定 |
|---|---|
| kernel 快，但完整 tick 无显著收益 | 不默认采用；定位同步/后处理，最多追加一个有明确目标的实验 |
| 密集场景收益≥30%，小场景退化 | 保留 CPU+CUDA 双路径，实测代边界切换成本与阈值 |
| CPU 优化后全部目标已达标，GPU 收益不足抵偿维护 | 交付 CPU，CUDA 文档/原型可保留但默认关闭 |
| GPU 收益达标但顺序或画面不一致 | 正确性失败，不采用 |
| GPU 解决服务端，但网络/客户端仍超预算 | 项目整体未达标，继续对应瓶颈工作 |
| GPU 与完整管线均通过，部署/回退测试通过 | 作为可选正式后端发布，并记录支持设备范围 |

## 9. 风险清单与停止条件

| 风险 | 发现方式 | 应对 |
|---|---|---|
| 增量缓存漏写路径 | 随机回放、逐阶段对比 | 统一变更入口、补失效测试，不每代重建掩盖 |
| alive/Map 顺序改变 | 有序断言、AI 日志、小地图像素 | 顺序兼容层；收益不足则不启用该算法 |
| 小地图透明叠色不可精确复现 | 固定设备像素差异 | 保留原叠色重绘，寻求等价批处理；不自行放宽视觉约束 |
| 协议顺序元数据抵消压缩 | 完整线速与解码测量 | 自适应回退，报告真实边界 |
| worker 命令错代/重复 | seq/epoch 日志、故障注入 | 单房间屏障、恰好一次提交 |
| CUDA 平均快但长尾慢 | p99/max/排队与温控轨迹 | 预分配、减少同步、保留 CPU；不只报告 kernel |
| 浏览器后台限频或慢网 | 代序列、队列、visibility 记录 | 独立恢复测试，剔除实时认证范围但不隐藏失败事件 |
| 基准热身后负载消失 | L/C/D 与 finished 断言 | 重建一致预热状态，区分合成/实战 |
| 同机 GPU 计算抢浏览器资源 | 服务端与浏览器同机/分机对照 | 选择 GPU 预算/后端，不假设二者互不影响 |

任何一项优化出现未解释的规则或画面差异，暂停该项推进；先定位，不用后续优化掩盖。仅对该路线停止，不要求撤销已经独立通过的优化。
